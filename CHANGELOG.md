# Changelog - learning-sprint

All notable changes to this skill, newest first.

## 2026-09-10 (grader fairness: the colon and `alt`)
- **`toks()` now splits on `[\s,.;:]+`, with the colon**, and `norm()` strips trailing `[.;:]+`. No rule-count change (still 28); this amends the canonical grader contract in `workbook-template.md` Part 2, which rule 23 points at. When a subject prints names in a form that carries a colon, a learner who copies them exactly as the drill printed them produces tokens that all end in a colon and **fails a fully correct answer**. Found on API Session 2, whose signal-vs-plumbing drill shows a real HTTP header list (`content-type: application/json`, `etag: W/"..."`) and asks for the header names back: `content-type:, etag:, x-ratelimit-remaining:` was graded wrong. Earlier tracks stripped the colon in `norm()` only, so `value` answers were safe and every `set`/`seq` answer was not, which is why this survived four tracks. A sweep of all shipped tracks found one other genuine exposure, Git Session 8's reflog drill, whose scenario prints `HEAD@{1}: commit: ...` and asks for the `HEAD@{n}` labels back.
- **Added an optional per-drill `alt` array**: other accepted SPELLINGS of the same answer, tried after the exact match fails. A fairness fix, not a convenience. A quantity can honestly be typed as a digit or a word and no format nudge makes one of them the obviously-intended form, so a single accepted string turns understanding into a coin flip on wording. API Session 2 had one drill demanding `0` and another four items later demanding `two`: each individually defensible, arbitrary taken together. The contract states the invariant explicitly, that `alt` never accepts a DIFFERENT answer, only a different spelling of the correct one, and says to verify with a harness asserting the REJECTS as well as the accepts, since an over-broad `alt` silently stops the drill testing anything and no gate catches it.
- Recorded the preference order: widen `alt` rather than tighten the ask. "Answer with a digit, not a word" is a real instruction a learner can miss, and gating a correct understanding on it is the unfair grade rule 7 forbids.
- **Neither fix is visible to any of the five gates.** `scan_js`, `check-js`, `verify-session`, `verify-restore` and `check-quiz` all pass a grader that rejects correct answers, because the engine runs fine and emits cards either way. Only enumerating what a learner who understands might plausibly type finds this class, the same way rule 28's semantic half needs a human read rather than a ratio.
- Also recorded from the same build: `check-quiz.py` fails on the longest AND shortest heuristics, so aiming at 0/N on one alone walks into the inverted exploit (a first draft scored 0/5 longest and 5/5 shortest, a correct fail); the target shape is the correct option sitting mid-pack.

## 2026-08-31 (rule 28: colour contrast)
- **NEW rule 28, "every text colour must clear WCAG AA on every surface it sits on"** (new `## Colour and contrast` section; rule count 27 -> 28, Contents block and provenance paragraph updated, `SKILL.md`'s stale "26 rules as of 2026-07-17" corrected to 28 as of 2026-08-31). A text token must clear 4.5:1 against every container background in ITS OWN palette, in both light and dark mode. Nothing in a workbook qualifies for the relaxed 3:1 large-text allowance, so 4.5:1 applies down to the 10.5px micro-labels. The rule names the four ways it fails quietly: palettes differ per track so a ratio computed on one track is meaningless for another; failures cluster on a few tokens so chasing selectors hides the cause; each token is declared twice per mode (media query plus `[data-theme]` override) so fixing one leaves the theme toggle serving the old colour; and the mode you did not build in is the one that fails.
- **The semantic half is the part that actually bit.** A palette's faintest token exists for text meant to recede (uppercase micro-labels, counters, a shell name above a command) and must never carry prose. The failure was a `.note` box holding real instructions painted in that token. Passing 4.5:1 would not have made it right: prose belongs on a prose-weight token regardless of ratio.
- **Same-day amendment: rule 28 gained a text-on-FILL clause.** The first draft said to check text against container backgrounds, which misses the on-colour tokens that sit on a filled button or badge. Applying the rule to the animation sprint darkened its `--gold` for legibility on a pale ground and thereby drove the dark `--gold-ink` text sitting ON that gold fill from an already-failing 4.07 down to **2.44**. A fix in one place opened a worse failure in another, so the rule now says to re-audit the pairs after every token change. Caught before publishing only because the pairs were re-checked.
- Origin: the learner browser-checked Git Session 2 and said a note box was hard to read. Auditing all 56 text-on-background pairs in the shared stylesheet found **25 failing, worst case 2.81:1**, in all three shipped tracks plus the portal, and light mode failed worse than the dark mode the check happened in. Root cause was four pale tokens, not 25 bugs: the faint ink token (15 of the failures), plus success and warning in light mode, plus one track's accent. Fixed across 38 files by nudging tokens the minimum hue-preserving amount. **Every automated gate passed the whole time**, which is the point: like rule 15 (ligatures), the characters are all correct and the page renders fine, so only computing the ratios or a human on a real screen finds it. This is also the first rule contributed by a learner-side browser check rather than an editor pass.

## 2026-08-04 (rule 18: unrun cross-environment claims)
- **Extended rule 18 with a cross-environment clause.** No rule-count change (still 27); this sharpens an existing gate rather than adding one. A claim about a platform, shell, installer, or version you did not actually run is NOT covered by the run-and-diff gate and must not ship unqualified: running is authoritative only about the machine you ran on, so a sentence describing what some OTHER environment does is structurally invisible both to the gate and to the adversarial reviewer, who runs on the same machine and finds no contradiction. Three acceptable resolutions, in preference order: reproduce the other environment well enough to test it (override the relevant config, e.g. point `GIT_CONFIG_SYSTEM` at an empty file to simulate an install whose system config sets nothing, or pin the interpreter version); scope the claim explicitly to the environment you did verify ("on Windows you will see...") and say nothing about the others; or cut it. Contents summary line updated to match.
- Canonical case (Git Sprint S1): the session said that leaving `init.defaultBranch` unset makes Git "print a wall of hint text every single time you create a repository, nagging you to pick one." Verified true on a stock macOS or Linux install, and **false on Git for Windows**, where the installer's system config already sets `init.defaultbranch=master`, which satisfies Git, suppresses the hint, and silently produces `master`. The session declares PowerShell as its default shell, so it described a symptom its own primary audience never sees, and the learner therefore had no signal that they had skipped a setup step. It shipped, passed the gate, and was browser-checked before anyone caught it, because every check ran on the platform the sentence was not about.
- Second instance found the same day, same class, worse consequence (Python Sprint S6): the venv step showed `venv\Scripts\Activate.ps1` succeeding with no mention of PowerShell's execution policy. Fine under `RemoteSigned` (the build machine), fatal under `Restricted` (the Windows client default), where it fails with "cannot be loaded because running scripts is disabled on this system" and blocks the session's milestone plus every session after it. Two instances in one day is why this became a rule clause rather than a per-track note.
- **Recorded why the learner is the wrong backstop for this class of error.** They cannot know the subject yet, which is the entire reason they are taking the sprint, and they can only observe one environment, their own, so a wrong claim about a different one reads to them as simply true. Content correctness stays entirely the build session's burden, via rules 18 and 19, the JS gates, and the independent adversarial reviewer.

## 2026-07-09 (later)
- Sharpened rule 18 (no rule-count change, still 19): diff output EXACTLY, never rstrip/normalize trailing newlines or whitespace on both sides of the comparison, or the runner silently masks real learner-visible bugs.
