## 2026-07-16 (SQL Session 5, Parsons layout)
- Folded one lesson from building SQL Session 5 (subqueries + derived tables). No new numbered rule (still 20); a subject-agnostic refinement of the Parsons-layout guidance in workbook-template.md (and its pointer in editorial-rules.md). **Parsons full-width column is CONDITIONAL, not a blanket default.** The two-column side-by-side layout (`minmax(0, 1fr) minmax(0, 1fr)`) stays the default and gives each tile ~54 monospace chars, which is plenty for short tiles (most code, and non-code subjects like animation, language or cooking where a tile is a short step). Only when a sprint's Parsons lines will actually run past ~54 chars (verbose queries like SQL, long code lines) switch that sprint to a single full-width column (`grid-template-columns: 1fr`, bank stacked above the solution, ~115-char tile) so long clauses fit instead of getting a per-line horizontal scrollbar that fights the click-to-move interaction. Decide the layout ONCE per sprint and keep it consistent across all that sprint's sessions (a mid-sprint shape change reads as unfinished), but do NOT let a long-line subject's choice leak into short-line subjects. When full width is used, add a one-line blurb by the Parsons heading explaining the two stacked lists and click-to-move, since wide tiles look sparse on short-line sessions. Regardless of layout: keep one clause per tile, multi-line long subqueries / CTE bodies across tiles, and keep `overflow-x: auto` as a never-triggered safety net. Found building the SQL sprint, whose derived-table clauses (77 chars) overflowed the two-column tiles; applied full width across all five SQL sessions for consistency, then corrected the skill so it does not prescribe full width for every subject. (Also this session: added a scalar-subquery single-value-rule DEMONSTRATION per rule 16, and fixed an ASCII side-by-side reference-table off-by-one where orders-only rows lacked a left-side row to inherit spacing from; both SQL-specific, logged in the sql-sprint project memory, not skill-level.)

## 2026-07-15
- Folded four lessons from building SQL Session 3 (aggregation + GROUP BY), the first non-trivial third session in a subject. No new numbered rule (still 20); all four are always-true refinements to existing rules, all subject-agnostic. (1) **Syntax-placeholder unpacking** (clause added to rule 1 in editorial-rules.md): when a taught form uses a stand-in the learner supplies (e.g. `COUNT(col)`), say once that the placeholder is not literal and keep the same placeholder word everywhere; avoid a placeholder that is real syntax in some dialect (`[name]` is a SQL-Server identifier quote). Found when prose wrote `COUNT(column)` but the example used `COUNT(referrer)` with no cue that `column` was a stand-in. (2) **Ask-must-not-leak** (clause added to rule 8): a predict-drill's question text may state the required output FORMAT but must never state the CONCEPT under test (a drill asking "what does COUNT(referrer) return? (COUNT skips NULLs)" gives away the rule it tests); distinguish a fair format nudge from a concept giveaway. (3) **Drill-task variety** (new paragraph in the drill-answer-variety rule + Part 2 in workbook-template.md + Part 2 mirror in domain-adaptation.md): answer-type spread (value/set/seq/count) is necessary but not sufficient, also vary the cognitive TASK and ramp easy-to-hard (read a whole result, operate on a subset, read one group, combine clauses), rather than restating the same move with a different function. Found when an aggregation section had 6 of 11 drills all "one aggregate over the whole table". (4) **Setup-fallback placement** (Part 1 in workbook-template.md + environment note in domain-adaptation.md): when a session mutates shared practice data or needs a from-zero rebuild, put the full-setup fallback directly under the primary setup script and ABOVE the "confirm the result" step, since the fallback is an alternative to the primary script and a learner who lost their environment needs it before being told to verify a result. Also updated the editorial-rules provenance note (SQL Sessions 1-2 -> 1-3).

## 2026-07-12
- Folded three lessons from building a SECOND sprint in a new subject (SQL, Sessions 1-2), the first non-Python use of the skill. No new numbered rule (still 20); all three are always-true refinements + step guidance, all subject-agnostic. (1) **Drill-answer-variety** (new always-true rule in editorial-rules.md + a Part 2 bullet in workbook-template.md): Part 2 predict drills must vary their ANSWER TYPE, not default to a count, which tests a proxy (how many pass) rather than the real skill (which results come back). Each drill gets an explicit `type` graded through a shared `gradeDrill(d, val)`: `count`/`value` exact-match via the normalizer; `set` (all results, any order) and `seq` (results in order) tokenize via `toks(s)=s.toLowerCase().trim().split(/[\s,.;]+/).filter(Boolean)` then sorted- or in-order-compare (separators/case/trailing-punct forgiven; missing/extra/mis-ordered fail). This shared grader is what makes "which results?" a fair deterministic drill instead of collapsing to counts. Also normalized a trailing `[.;]+` in the count/value path for the same forgiveness. Guidance added: ask `value` for one result, `set` for several, `count` only when the count is the lesson, `seq` only when the result is ordered; aim for a spread. Mirrored into domain-adaptation.md Part 2. (2) **Level-0 default + onboard the real environment FROM ZERO in Session 1** (SKILL.md Step 1 + Step 4 + domain-adaptation.md): default to a true level-0 beginner unless the intake says otherwise, and Session 1's first "Your turn" must set up the environment from nothing (how to GET / OPEN / WHERE), not just name it. This is rule 1 (unpack before use) applied to the environment. (3) **Gate the Part 4 "Reveal reference solution" button** (extends rule 20 in editorial-rules.md + Part 4 in workbook-template.md): disable it until the write-it textarea has content, so the learner attempts before peeking, same as every other gated control. Also added a code-example line-width note to workbook-template.md Build/QA (keep `<pre>` lines under ~100 visible chars so they do not h-scroll; put long result annotations on their own line) and made the domain-adaptation SQL environment row accurate (DB Browser for SQLite / sqlite3, not "DB Fiddle"). A Part 2 note also records that not every code subject has a clean visualizer (SQL has none), so drop the watch-it-run link when there is no faithful one.

## 2026-07-10
- Session 8 hardening (no rule-count change, still 19; two always-true notes + one template CSS fix). (1) Folded the recurring "comment telegraphs its own blank" offender into rule 8 in editorial-rules.md: a faded/Parsons inline comment must describe what the line DOES, never name the blanked token (seen S2/S4/S5/S8). (2) Added an "always-true artifact-integrity rule" to editorial-rules.md: neither the run-and-diff gate (rule 18, separate runtime) nor the taught-trace (rule 19) checks that the artifact's own JS parses, so after ANY edit to a JS string literal (a data-array entry, even a comment inside one) re-validate the <script> before publishing, via a tokenizer that flags unterminated quoted literals at line breaks plus a bracket-balance pass (no JS engine needed). ## 2026-07-09 (later)
- Sharpened rule 18 (no rule-count change, still 19): diff output EXACTLY, never rstrip/normalize trailing newlines or whitespace on both sides of the comparison, or the runner silently masks real learner-visible bugs. Canonical case from Python Sprint Session 5: `print(open(path).read())` leaves a trailing blank line whenever the file ends in a newline (most editors add one), which a rstrip-both-sides harness passed on the first audit and only a strict re-run caught. Also folded into teaching guidance: `.read()` keeps the final newline, a concrete reason to prefer iterating lines plus a per-line strip.
